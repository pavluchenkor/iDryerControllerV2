# UART/TLV протокол для iDryerRP2040

## Цель
Обеспечить единый двунаправленный канал между RP2040 и мостами (ESP32, тач-экран, ПК), через который можно безопасно читать/писать меню (`src/menu/menu_v2.yaml`) и обмениваться вспомогательными данными (телеметрия, события). Протокол рассчитан на работу поверх UART и может быть прозрачно ретранслирован по TCP/WebSocket/HTTP.

## Формат кадра
| Поле           | Размер | Описание                                                |
|----------------|--------|----------------------------------------------------------|
| Preamble       | 1      | `0xAA` — старт кадра                                     |
| Version        | 1      | Номер версии протокола (например, `0x01`)                |
| Msg Type       | 1      | Код сообщения (`HELLO`, `SET_VALUE`, `INVOKE_ACTION`…)   |
| Msg ID         | 2      | Счётчик запроса/ответа (little-endian)                   |
| Payload Length | 1      | Количество байт TLV-блока                                |
| Payload (TLV*) | N      | Последовательность TLV (см. ниже)                        |
| CRC16          | 2      | CRC16-IBM по байтам от Preamble до конца Payload         |

## TLV-типы (базовый набор)
| Type | Значение             |
|------|----------------------|
| 0x10 | `MENU_ID` (2 байта)  |
| 0x11 | `CTRL_INDEX` (1 байт)|
| 0x12 | `UNIT_ID` (доп. канал для подписок) |
| 0x20 | `STATUS` (1 байт)    |
| 0x30 | `VALUE` (1/2/4 байта в зависимости от `vtype`) |
| 0x40 | `TIMESTAMP` (`uint32_t`) |
| 0x50 | `TELEMETRY_KEY` (1 байт) |
| 0x51 | `TELEMETRY_VALUE` (float/uint32) |

TLV — это `type | length | value`. Например, `10 02 00 03` означает: тип `0x10`, длина `0x02`, значение `0x0003` (`MENU_DRY_TEMP`).

## Типы сообщений
| MsgType | Назначение |
|---------|------------|
| 0x01 `HELLO` | Обмен версиями и битовой маской возможностей (например, поддержка телеметрии, подписок). |
| 0x02 `SET_VALUE` | Запись значений узлов меню. |
| 0x03 `INVOKE_ACTION` | Запуск action-узла (`start_drying`, `start_storage`). |
| 0x04 `GET_VALUE` | Чтение текущего значения (ответ — `VALUE_REPORT`). |
| 0x05 `SYNC_SNAPSHOT` | Массовый дамп состояний (использует `menu_state_dump.*`). |
| 0x06 `SUBSCRIBE` | Запрос на подписку на изменения/телеметрию. |
| 0x07 `UNSUBSCRIBE` | Снятие подписки. |
| 0x10 `MENU_EVENT` | Асинхронные уведомления о смене значений или окончании действий. |
| 0x11 `TELEMETRY` | Свободный канал для параметров, которых нет в меню. |
| 0x81 `ACK` | Подтверждение (в Payload достаточно `STATUS=0x00`). |
| 0x82 `ERROR` | Ошибка, TLV `STATUS` = код ошибки, опционально TLV `VALUE` с деталями. |

## Примеры кадров
### Установка температуры сушки = 55 °C для контроллера 0
```
AA 01 02 10 42 0D  10 02 00 03  11 01 00  30 04 42 5C 00 00  2B 7F
```
1. `MENU_ID = 0x0003` (`MENU_DRY_TEMP` из `src/menu/menu_ids.h:3`).  
2. `CTRL_INDEX = 0` (первый контроллер; TLV `11 01 00`).  
3. `VALUE = 42 5C 00 00` (float 55.0).  
4. Прошивка применяет значение (см. алгоритм ниже), отправляет `ACK` с тем же `msg_id`.

### Запуск хранения для контроллера 1
```
AA 01 03 10 43 08  10 02 00 0A  11 01 01  7A B1
```
- `MENU_ID = 0x000A` (`MENU_STORAGE_START` в `src/menu/menu_ids.h:11`).  
- `CTRL_INDEX = 1`.  
- Action без TLV `VALUE`, прошивка вызывает `start_storage()` и отвечает `ACK` либо `ERROR`.

## Детальный разбор обработки на RP2040
1. **Парсинг кадра.** Проверить преамбулу, версию, длину, CRC и разобрать TLV. После разбора от `SET_VALUE` остаётся, например, `MENU_ID=0x0003`, `CTRL_INDEX=0`, `VALUE=55.0f`.  
2. **Доступ к описанию узла.** `const MenuItem& item = g_menu[menu_id];` (таблица генерируется в `src/menu/menu_data.cpp:51`). Для `0x0003` это запись `MENU_DRY_TEMP` (`src/menu/menu_data.cpp:70`), где указаны тип `MN_VALUE`, границы и указатель на `menu.dry_temp`.  
3. **Проверка типа сообщения.** `SET_VALUE` разрешён только для `MN_VALUE`/`MN_TOGGLE`. Если узел `SCOPE_PER_CONTROLLER`, индекс берётся из TLV `CTRL_INDEX` и передаётся как `idx`.  
4. **Применение.** Используем готовые утилиты из `menu_bindings`: `store_value()` и `menu_apply_by_bind()` (`src/menu/menu_bindings.cpp:114` и `151`). Они:
   - конвертируют float в нужный `vtype` (`VT_F32`, `VT_U16`, `VT_BOOL` и т.д.),  
   - пишут значение либо прямо в поле структуры `menu` (`src/menu/menu_state.cpp:11`), либо в массив `[idx]`,  
   - при `persist=true` вычисляют офсет EEPROM (`calc_eeprom_offset()`, `src/menu/menu_bindings.cpp:136`) и вызывают `ee_store_field`.  
5. **Колбеки.** Если у узла есть `on_change`, она вызовется автоматически (`menu_apply_by_bind()`, строки `158‑169`). Для action узлов вместо записи вызывается `item.action.fn()` (например, `start_storage()` объявлена в `src/menu/menu_data.cpp:17`).  
6. **Ответ.** При успехе — `ACK` (`STATUS=0x00`). Нарушение границ/типов или отсутствие узла → `ERROR` с кодом проблемы. Асинхронные изменения публикуются отдельными кадрами `MENU_EVENT`.

## Направление обмена
- **Входящие в RP2040 (host → MCU):** `HELLO`, `SET_VALUE`, `GET_VALUE`, `INVOKE_ACTION`, `SUBSCRIBE`, `UNSUBSCRIBE`. Они изменяют `MenuState` или запускают действия.  
- **Исходящие из RP2040 (MCU → host):** `ACK/ERROR` (на каждый запрос), `MENU_EVENT` (любая смена значения или завершение action), `SYNC_SNAPSHOT` (ответ на запрос или по таймеру), `TELEMETRY` (доп. данные), `KEEPALIVE` (если нужно).  

ESP32/тач-экран ведёт себя как мост: UART ↔ Wi-Fi, без собственной логики. Он должен дожидаться `ACK` перед тем как проксировать следующую команду от внешнего клиента, чтобы не создавать гонок, и, по желанию, кэшировать `MENU_EVENT` для новых подключений.

## Телеметрия и данные вне меню
Некоторые параметры (температуры датчиков, токи, статусы PID) не входят в дерево меню. Их можно передавать двумя способами:
1. **Отдельные TLV в существующих сообщениях.** Например, в `MENU_EVENT` добавить `TELEMETRY_KEY`/`TELEMETRY_VALUE`, если событие привязано к конкретному узлу.
2. **Выделенный MsgType `TELEMETRY` (0x11).** Payload содержит:
   - `TELEMETRY_KEY` — короткий ID (можно завести enum `TelemetryKey` в `include/telemetry_ids.h`).  
   - `UNIT_ID` или `CTRL_INDEX`, если данные привязаны к конкретному контроллеру.  
   - `TELEMETRY_VALUE` (float/uint32/строка — можно добавить тип в TLV).  

Для подписок клиент отправляет `SUBSCRIBE` с TLV `TELEMETRY_KEY` и опционально `CTRL_INDEX`. MCU ведёт список подписчиков и отправляет `TELEMETRY` кадры только при изменении значений. Так можно транслировать: реальные температуры нагревателей, состояние вентиляторов, ошибки, логическую фазу процесса.

## Как меню превращается в код
1. **Исходный YAML.** Весь интерфейс описан в `src/menu/menu_v2.yaml`. Запуск генератора (`python src/menu/generator/gen_menu_v2.py src/menu/menu_v2.yaml --out src/menu`) пересоздаёт набор файлов.  
2. **ID узлов.** `src/menu/menu_ids.h:3` содержит `typedef enum MenuId`, где перечислены все `MENU_*`. Компилятор присваивает последовательные значения, начиная с `0`. Эти числа попадают в протокол (`MENU_ID`).  
3. **Состояние.** `src/menu/menu_state.h`/`.cpp` (`menu_state.cpp:11`) объявляют структуру `MenuState menu;`. В ней есть поля `dry_temp`, `storage_temp`, `preset_*` и т.д., а также функции `initDefaults()`/`loadFromEEPROM()`/`saveToEEPROM()` (см. `menu_eeprom_io.*`).  
4. **Типы и границы.** `src/menu/menu_types.h` определяет `VT_F32`, `VT_U16`, `VT_BOOL` и enum `MenuNodeType`. Эти значения появляются в `g_menu` и `g_bindings`, чтобы код понимал, как интерпретировать TLV `VALUE`.  
5. **Дерево меню.** `src/menu/menu_data.cpp:51` содержит массив `g_menu[MENU__COUNT]`. Для каждого элемента там описаны: родитель, дети, тип узла (`MN_VALUE`, `MN_ACTION`), текст для UI, диапазоны `min/max/step`, указатель на поле в `menu`, указатель на функцию `on_invoke`. Action-узлы (например, `MENU_DRY_START`) ссылаются на реальные функции (`start_drying()` объявлены в верхней части файла).  
6. **Привязки.** `src/menu/menu_bindings.cpp:27` генерирует массив `g_bindings`. Запись связывает строковый `bind` (из YAML `bind:`), `vtype`, `scope`, указатель на память в структуре `menu`, EEPROM-смещение и функцию `on_change`. Именно эта таблица используется обычным меню (см. `menu_apply_by_bind()`), и её можно напрямую использовать в протоколе, чтобы не писать дополнительных `switch`.  
7. **Weak callbacks.** Пользовательские обработчики можно определить в `src/menu/user_menu_callbacks.cpp`, при этом генератор кладёт weak-реализации в `src/menu/menu_callbacks_weak.cpp`, чтобы линковка прошла даже без реализации.  

Благодаря этой автогенерации протоколу не нужно вручную мапить «какой ID к какой переменной относится»: `MENU_ID` → индекс в `g_menu` → указатель на нужное поле `MenuState` и метаданные (`vtype`, `scope`, `persist`). Обратным путём можно получить `bind` или имя функции для логов/телеметрии.

### Пример соответствий
- `MENU_DRY_TEMP = 3` (`src/menu/menu_ids.h:4`). В `g_menu[3]` (`src/menu/menu_data.cpp:70`) указано, что это `MN_VALUE`, тип `VT_F32`, диапазон `30…110`, указатель на `menu.dry_temp` и `scope = SCOPE_PER_CONTROLLER`. Соответствующая запись в `g_bindings` (`src/menu/menu_bindings.cpp:29`) ссылается на тот же массив и определяет EEPROM-офсет `2221`.  
- `MENU_STORAGE_START = 10` (`src/menu/menu_ids.h:11`). В `g_menu[10]` (`src/menu/menu_data.cpp:90`) тип `MN_ACTION`, функция `start_storage`. Для action нет записи в `g_bindings`, но протокол может напрямую вызвать функцию через `item.action`.  
- Любая новая переменная, добавленная в `menu_v2.yaml`, автоматически появится во всех перечисленных файлах, поэтому протокол не требует ручной синхронизации: достаточно использовать `MENU_ID` и `CTRL_INDEX`, и остальное подтянется из автогенерированных таблиц.

## Рекомендации по реализации
1. Реализуйте общую библиотеку сериализации/десериализации кадров (RP2040 ↔ ESP32) с таблицей TLV типов.  
2. Добавьте модуль `protocol_handler.cpp`, который связывает сообщения с `g_menu`/`menu_bindings`.  
3. Документируйте новые TLV и коды ошибок прямо в этом файле, чтобы UI/серверы могли автоматически генерировать клиентские части.  
4. Напишите тест, который прогоняет все `MENU_*` ID: формирует кадр `SET_VALUE`, проверяет, что соответствующее поле `menu` обновилось и EEPROM записалось (можно использовать unit test/Host test).  
5. Расширение протокола (телеметрия, подписки) делайте через `HELLO` (битовая маска возможностей). Клиент сначала узнаёт, какие функции доступны, и только потом использует их.
