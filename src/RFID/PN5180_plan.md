# RFID: план перехода на PN5180

## Цель

Зафиксировать, почему `PN532` уже выполнил свою роль в проекте, и что именно нужно сделать для перехода на `PN5180` как целевой RFID/NFC-платформы под `OpenPrintTag`.

## Что уже доказал PN532

Текущий этап с `PN532` не был потрачен зря. Он уже подтвердил базовую архитектуру проекта:

- контроллер умеет жить с неблокирующим `RFID`-драйвером;
- `IRQ-assisted` детект метки на RP2040 работает;
- UID-детект отделен от чтения содержимого;
- чтение/запись можно строить в двух режимах:
  - `Sync`
  - `Async`
- чтение/запись можно разбивать на шаги, чтобы не ломать основной цикл;
- логика `detect -> read -> write -> verify` и все тайминги уже есть и могут быть переиспользованы;
- протокол с бэкендом уже можно строить вокруг:
  - полного образа метки;
  - частичного patch-обновления;
  - отдельного verify.

То есть `PN532` был полезен как:

- быстрый стенд;
- proof-of-concept для архитектуры;
- место, где были сняты реальные тайминги и найдены узкие места.

## Почему PN532 не является финальным решением

`PN532` подходит для `NTAG21x / ISO14443A`, но не подходит для официального целевого стека `OpenPrintTag`.

Главная причина:

- `OpenPrintTag` ориентирован на `NFC-V / ISO15693`;
- `PN532` этот режим не поддерживает;
- `OpenPrintTag` проектировался под `ICODE SLIX2 320B`;
- для полной совместимости с телефоном, iPhone и спецификацией нужен другой чип.

Следствие:

- `PN532` остается полезным только как промежуточный dev/R&D этап;
- production-ветка должна идти в `PN5180`.

## Почему выбран PN5180

`PN5180` подходит по направлению развития проекта:

- поддерживает `ISO15693 / NFC-V`;
- подходит под `ICODE SLIX2`;
- лучше соответствует `OpenPrintTag`;
- позволяет сохранить почти весь уже сделанный верхний слой:
  - `IRfidDriver`
  - manager
  - state machine операций
  - `Sync/Async` transfer
  - verify
  - patch/full write модель

Идея перехода:

- не переписывать весь RFID-стек;
- заменить только конкретный чиповый драйвер:
  - `Pn532Driver` -> `Pn5180Driver`.

## Что у нас есть по пинам на текущей плате

Текущая колодка подходит для **одного** `PN5180` без отдельного `IRQ`.

Доступные линии:

- `GPIO12` -> `MISO`
- `GPIO13` -> `BUSY`
- `GPIO14` -> `SCK`
- `GPIO15` -> `MOSI`
- `GPIO18` -> `RST`
- `GPIO19` -> `NSS`

Питание:

- `+5V`
- `+3.3V`
- `GND`

### Вывод по железу

Для одного `PN5180` пинов хватает.

Нюансы:

- `NSS` нельзя зафиксировать постоянно в одном состоянии, это полноценный `chip select` каждой SPI-транзакции;
- `BUSY` для `PN5180` обязателен;
- отдельного свободного GPIO под `IRQ` на текущей колодке уже не остается;
- для базовой работы `IRQ` не обязателен, можно опираться только на `BUSY`.

### Что не помещается

На текущей разводке **не помещаются**:

- два `PN5180`;
- один `PN5180` с отдельным `IRQ`, если не отказываться от текущих обязательных линий;
- полноценная multi-reader схема без новой ревизии платы.

## Что значит BUSY-ориентированный драйвер

Для `PN5180` целевой режим работы должен быть не `interrupt-first`, а `BUSY-first`.

Это означает:

- MCU начинает SPI-команду;
- драйвер не крутит тяжелое ожидание в одном длинном blocking-вызове;
- вне ISR или вообще без ISR драйвер смотрит на `BUSY`;
- когда `BUSY` разрешает продолжить обмен, драйвер читает ответ;
- чтение и запись блоков строятся как state machine.

Итог:

- отдельный `IRQ` не критичен;
- `BUSY` достаточно, чтобы сделать неблокирующий драйвер;
- по архитектуре это очень похоже на то, что уже было сделано для `PN532`.

## Какие библиотеки были рассмотрены

### 1. `ATrappmann/PN5180-Library`

Плюсы:

- самый полезный донор по функциональности;
- есть `ISO15693`;
- есть `readSingleBlock` / `writeSingleBlock`;
- есть `SLIX2`-специфичные команды;
- много `fork`.

Минусы:

- репозиторий архивирован;
- как живую production-зависимость брать не стоит.

### 2. `playfultechnology/PN5180`

Плюсы:

- простой;
- хорошо показывает базовую схему работы через `BUSY`.

Минусы:

- слишком узкий;
- больше подходит для `inventory`/UID;
- слаб как основа для полноценных `read/write/verify` операций.

### 3. `dotnet/iot` / `nanoFramework` реализация PN5180

Плюсы:

- хороший зрелый референс по API;
- есть `ReadSingleBlock`, `WriteSingleBlock`, `ReadMultipleBlocks`, `ISO15693`;
- хорош как образец архитектуры.

Минусы:

- это не Arduino/RP2040 библиотека;
- код нельзя просто взять как drop-in replacement.

### Вывод по библиотекам

Готовой идеальной Arduino-библиотеки под наш проект не найдено.

Лучший путь:

- не тащить чужую библиотеку целиком;
- взять `ATrappmann` как функциональный донор;
- взять `dotnet/iot` как архитектурный референс;
- написать свой локальный `Pn5180Driver` под текущий проект.

## Какой формат данных считать целевым

Нужно разделять два уровня:

### 1. Физический носитель / транспорт на теге

Целевой формат:

- `ISO15693`
- `SLIX2`
- `OpenPrintTag`

### 2. Логика записи со стороны прошивки

Прошивка не должна собирать `OpenPrintTag` из JSON.

Правильная модель:

- бэкенд формирует готовый бинарный образ;
- RP2040 принимает его как `opaque bytes`;
- RP2040 не парсит содержимое;
- RP2040 умеет:
  - записать образ;
  - прочитать обратно;
  - сверить байты;
  - при необходимости записать только patch.

## Модель записи

Нужно поддержать два режима:

### 1. Full write

Используется, когда:

- пользователь изменил настройки;
- материал или профиль изменился целиком;
- нужно полностью заменить запись на метке.

### 2. Patch write

Используется, когда:

- в процессе работы меняется только вес;
- формат гарантирует стабильное расположение поля веса;
- бэкенд знает, какие байты или блоки реально изменились.

Важное условие:

- patch по весу имеет смысл только если поле веса в бинарнике не плавает по длине;
- это задача бэкенда и формата;
- прошивка должна лишь уметь применить patch к нужным блокам.

## Что уже можно переиспользовать из текущего кода

Переиспользуется почти весь верхний слой:

- `IRfidDriver`
- `RfidManager`
- события `TagDetected` / `TagRemoved`
- `Sync/Async` модель операций
- verify после записи
- сборка/разбор буфера по фрагментам
- логирование и тайминг операций

Нужно заменить только чиповую часть:

- `Pn532Driver`
- transport/spi flow
- поблочные команды чтения/записи
- detect/inventory под `ISO15693`

## Подтвержденный итог по PN532

Этот раздел нужен как handoff для следующей сессии. По `PN532` уже получены практические ответы, и дальше эту ветку полировать не нужно.

### Что подтверждено на железе

- `IRQ-assisted` UID-детект работает стабильно;
- `TagDetected` / `TagRemoved` работают после debounce;
- отделение UID-детекта от чтения содержимого работает;
- верхний слой `Sync/Async` операций и verify уже собран и пригоден к переиспользованию;
- `NTAG215` читается стабильно;
- запись на `NTAG215` технически возможна;
- полное readback-verify после записи технически возможно.

### Реально измеренные времена на текущем стенде

- UID detect: примерно `23..30 ms`;
- preview read `32 bytes`: примерно `94..95 ms`;
- успешная запись тестового диапазона `308 bytes` на `NTAG215`: примерно `500..968 ms`;
- успешный readback того же диапазона: примерно `~898 ms`;
- худший одиночный шаг во время read/write: примерно `10..13 ms`.

### Что важно про запись на PN532

Запись на `PN532 + NTAG215` оказалась не полностью детерминированной:

- часть циклов `write + readback + compare` проходит успешно;
- часть циклов падает сразу на первой странице с ответом `status=0x27`;
- после исправления локального форка ложноположительного `write OK` больше нет;
- успешные циклы действительно сохраняют данные на метке и подтверждаются readback.

Практический вывод:

- `PN532` годится как dev/R&D стек;
- `PN532` годится для detect/read и для сервисных записей;
- любая запись на этом стеке обязана использовать:
  - retry;
  - readback verify;
  - честный отчет об ошибке вверх.

### Важные ограничения, которые уже не нужно переоткрывать

- для `NTAG21x` нельзя обращаться с `page 3` как с обычной user page;
- тестовый путь для `PN532` должен писать только user area, начиная с `page 4`;
- текущая логика RFID removal намеренно отвязана от весов на этапе bring-up;
- ручной ввод команд через `PlatformIO monitor` в `VS Code` показал себя ненадежным, поэтому self-test гонялся автоматически по стабильному появлению метки.

### Решение по PN532

- `lib/pn532` оставить в репозитории как рабочий стенд и запасной dev-инструмент;
- `lib/pn532` не удалять при переходе на `PN5180`;
- `PN532` считать резервным способом работы с меткой с ограниченным функционалом:
  - detect/read;
  - сервисные записи;
  - dev/diagnostic сценарии;
- `lib/pn532` и `Pn532Driver` больше не дорабатывать, кроме критичных bugfix по необходимости;
- новую разработку начинать только в:
  - `lib/pn5180`
  - `src/RFID/drivers/Pn5180Driver.*`

## Финальное решение

На текущем этапе проект фиксирует следующее:

- `PN532` был полезным промежуточным этапом и не является ошибкой;
- production-направление RFID должно идти в `PN5180`;
- текущая плата позволяет поднять **один** `PN5180`;
- отдельный `IRQ` для первой версии не обязателен;
- драйвер нужно строить вокруг `SPI + BUSY + state machine`;
- запись должна поддерживать оба режима:
  - полный образ;
  - частичный patch;
- формат должен собираться на бэкенде, а не на MCU.
