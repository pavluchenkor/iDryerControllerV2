# RFID: smart polling, запись веса на метку, almost interrupt-style

## Цель

Снизить влияние RFID на основной цикл RP2040 без потери надежности:

- не опрашивать PN532 агрессивно, когда по контексту смена катушки маловероятна;
- не записывать вес на метку слишком часто и в плохой момент;
- подготовить архитектуру к почти `interrupt-style` схеме, но не сломать текущую стабильную `SPI`-интеграцию.

## Текущее состояние

- Проект использует `Seeed-Studio/PN532` через `SPI` (`-DNFC_INTERFACE_SPI`).
- В `serviceTasks()` опрос идет каждые `200 мс` для всех ридеров подряд.
- Каждый `poll()` вызывает `readPassiveTargetID(..., 100)`, то есть потенциально блокирует цикл до `100 мс` на ридер.
- При двух ридерах без метки суммарная блокировка может доходить примерно до `200 мс` за один RFID-проход.
- Весы уже читаются неблокирующе и дают нетто/брутто вес по каждому юниту.
- `WriteRfid` еще не реализован, автоматической синхронизации веса на метку нет.

## Главная идея

Не переводить RFID на `UART/HSU` ради самого интерфейса. Основная проблема не в `SPI`, а в блокирующей модели библиотеки и слишком частом опросе в ситуациях, где смена катушки почти невозможна.

Нужна трехуровневая стратегия:

1. Умный gating опроса по состоянию юнита и тренду веса.
2. Ступенчатый polling budget: быстрый только когда есть шанс события, редкий когда катушка "заблокирована контекстом".
3. Только после этого оценивать переход к почти `interrupt-style`, и только если железо и библиотека это реально позволяют.

## Что считать "катушка не должна меняться"

Для юнита вводится состояние `spool_locked_by_context`.

Оно истинно, если одновременно выполняются условия:

- режим юнита не `Idle` и не `Error`;
- весы для юнита доступны;
- брутто-вес выше порога наличия катушки на платформе;
- тренд веса выглядит как "стабильно" или "медленно убывает";
- нет свежего резкого скачка веса вверх/вниз;
- нет ручного действия, которое обычно сопровождает смену катушки.

Это состояние не означает "метку нельзя читать вообще". Оно означает:

- не запускать частый polling;
- не делать тяжелое чтение содержимого метки;
- не инициировать запись на метку без отдельного условия.

## Критерии по весу

Нужен отдельный `WeightTrendState` на каждый юнит. Он не должен брать сырые значения, только уже отфильтрованный `HX711Multi::getMassMulti()` и `getMassBruttoMulti()`.

Минимальный набор полей:

- `last_mass_g`
- `last_brutto_g`
- `ema_slope_g_per_min`
- `window_delta_g`
- `noise_band_g`
- `stable_since_ms`
- `last_jump_ms`

### Базовые состояния

`NoSpool`

- `brutto < RFID_WEIGHT_PRESENT_MIN_G`

`Stable`

- за окно `Tstable` абсолютное изменение веса не больше `stable_band_g`
- мгновенные колебания не превышают `noise_band_g`

`SlowDecrease`

- тренд отрицательный, но в допустимом диапазоне "печать/естественный расход"
- нет резкого скачка вниз

`Unstable`

- любые быстрые изменения, колебания выше нормы, скачок вверх, скачок вниз, только что поставили катушку, только что коснулись платформы

### Практические пороги

Пороги нужно вынести в константы и откалибровать по логам, а не зашивать как догму.

Стартовые ориентиры для первой итерации:

- `RFID_WEIGHT_PRESENT_MIN_G = 80..120`
- `RFID_STABLE_WINDOW_MS = 15000..30000`
- `RFID_STABLE_BAND_G = 2..5`
- `RFID_JUMP_G = 15..30`
- `RFID_FAST_DROP_G_PER_MIN` подобрать по реальным логам печати

Важно: допустимая скорость убывания веса сильно зависит от реальной подачи филамента. Поэтому сначала надо накопить логи, потом зафиксировать порог.

## Политика опроса RFID

Опрос должен стать адаптивным.

### Состояния опроса

`FastScan`

- использовать при `Idle`, сразу после boot, сразу после снятия/установки катушки, при отсутствии стабильных весов
- период опроса: `150..250 мс`
- таймаут PN532 уменьшить до `20..30 мс`, а не `100 мс`

`SlowScan`

- использовать, если юнит активен и катушка `spool_locked_by_context`
- период опроса: `2..5 с`
- задача режима: ловить редкие реальные изменения, но не грузить loop

`ConfirmScan`

- временный усиленный режим после подозрительного скачка веса
- период: `100..200 мс` на короткое окно `2..5 с`
- нужен, чтобы быстро подтвердить реальную замену катушки

### Важное ограничение

Даже в `SlowScan` нельзя выключать polling полностью. Иначе система не увидит редкую реальную замену катушки во время активного режима.

### Сериализация ридеров

Не опрашивать два PN532 в одном проходе подряд, если этого можно избежать.

Нужна round-robin схема:

- в один RFID-тик обслуживается только один ридер;
- следующий ридер идет в следующий тик;
- тяжелое чтение содержимого метки никогда не выполняется в том же тике, где идет обычный inventory у другого ридера.

Это даст более ровную нагрузку на loop и сократит пиковые паузы.

## Когда не читать содержимое метки

UID можно получать быстро, но полный `readRaw()` нужно отделить от детекта.

Полное чтение метки не запускать, если:

- юнит в активном режиме и вес `Stable` или `SlowDecrease`;
- недавно уже был успешный `TagDetected` для того же UID;
- нет запроса от портала или необходимости верификации;
- идет окно повышенной чувствительности UART или критичный сервисный цикл.

Полное чтение запускать только если:

- UID новый;
- портал явно запросил чтение;
- нужна верификация после записи;
- после boot надо восстановить контекст для уже установленной катушки.

## Критерий для записи веса на метку

Портал не должен пушить запись на каждый новый весовой кадр.

Нужен принцип `desired tag state`:

- портал вычисляет, каким должен быть payload на метке;
- сравнивает его с последней подтвержденной записью;
- отправляет `WriteRfid` только когда разница значима и момент безопасен.

### Что считать значимым изменением

Запись разрешается, если выполняется хотя бы одно:

- изменился payload version/schema;
- изменилась привязка катушки или метаданные материала;
- изменился вес больше чем на `WRITE_WEIGHT_DELTA_G`;
- изменился вес больше чем на `WRITE_WEIGHT_DELTA_PCT` процентов;
- прошло больше `WRITE_MAX_AGE_MS` с последней подтвержденной записи.

Стартовые ориентиры:

- `WRITE_WEIGHT_DELTA_G = 20..50`
- `WRITE_WEIGHT_DELTA_PCT = 3..5`
- `WRITE_MIN_INTERVAL_MS = 10..30 min`
- `WRITE_MAX_AGE_MS = 6..24 h`

### Что считать безопасным моментом для записи

Портал может инициировать `WriteRfid` только если:

- UID метки стабилен не меньше `TAG_SETTLE_MS`;
- весовой статус `Stable`, а не `Unstable`;
- нет резкого скачка веса в последние `jump_guard_ms`;
- нет уже идущей операции чтения/записи;
- нет неподтвержденной предыдущей записи;
- контроллер не в состоянии ошибки;
- с момента `TagDetected` прошло достаточно времени для стабилизации поля и катушки.

### Чего не делать

- не писать во время каждого плавного уменьшения веса;
- не писать сразу после `TagDetected`;
- не писать, пока катушка шатается на весах;
- не писать без последующего readback verify.

## Требования к MCU для безопасной записи

Автозапись на стороне портала нельзя включать, пока на MCU нет полного цикла:

1. принять фрагменты `WriteRfid`;
2. собрать буфер;
3. проверить, что целевой тег все еще тот же UID;
4. записать данные;
5. перечитать записанный диапазон;
6. сравнить с исходным буфером;
7. отправить явный результат записи и код ошибки.

Минимальные коды результата:

- `ok`
- `tag_lost`
- `tag_changed`
- `busy`
- `verify_failed`
- `write_failed`
- `not_supported`
- `size_error`

Без `readback verify` автообновление веса на метке включать нельзя.

## Almost interrupt-style: что это должно означать

Не настоящий "весь PN532 на прерываниях", а гибрид:

- ISR на GPIO IRQ только отмечает факт события;
- вся работа с `SPI`, парсингом ответа и state machine идет вне ISR;
- если IRQ недоступен, система продолжает работать в адаптивном polling.

То есть цель не "читать метку внутри прерывания", а "не дергать PN532 без причины и быстро просыпаться, когда он сам говорит о событии".

## Главные проблемы перехода к almost interrupt-style

### 1. Текущая библиотека не дает готовый неблокирующий API завершения

В `Seeed-Studio/PN532` есть `startPassiveTargetIDDetection()`, но нет полноценного публичного API вида:

- `beginAsyncDetect()`
- `pollAsyncResult()`
- `consumeAsyncResult()`

С текущим API почти наверняка придется:

- форкать библиотеку;
- или писать свою тонкую обертку поверх transport-слоя;
- или выносить часть логики PN532 в проект.

Это главный риск, а не сам `IRQ`.

### 2. Нельзя вызывать PN532/SPI из ISR

В ISR допустимы только:

- установка `volatile` флага;
- запись timestamp;
- возможно инкремент счетчика событий.

Нельзя в ISR:

- дергать `SPI`;
- вызывать `readResponse()`;
- писать в `Serial`;
- лезть в `new/delete`;
- запускать тяжелую логику сравнения UID.

### 3. Нужны реальные IRQ-линии на железе

Для almost interrupt-style у каждого ридера нужна своя IRQ-линия, либо продуманное мультиплексирование событий.

Нужно проверить:

- выведен ли `IRQ` с каждого PN532-модуля;
- есть ли свободные GPIO на текущей ревизии платы;
- не конфликтуют ли они с UART, кнопками, экраном, сервой и Link.

Если IRQ физически не разведен, переход невозможен без переделки платы.

### 4. Поведение IRQ у PN532 надо валидировать на реальном железе

Нужно подтвердить экспериментально:

- когда именно линия `IRQ` опускается;
- снимается ли она после чтения ответа;
- нет ли ложных срабатываний после boot/reset;
- как линия ведет себя при двух ридерах на общей SPI-шине.

Без аппаратной валидации проектировать только по README нельзя.

### 5. Нужен re-arm протокол

После обработки события ридер должен снова войти в режим ожидания.

Нужно четко определить:

- когда отправлять новый `startPassiveTargetIDDetection()`;
- что делать после `TagRemoved`;
- нужно ли делать `inRelease()`/reset/rearm для конкретного сценария.

Ошибка здесь даст зависший ридер: метка ушла, а новые события больше не приходят.

### 6. Два ридера на одной SPI-шине усложняют модель

Даже при наличии двух IRQ:

- читать их одновременно нельзя;
- нужен единый диспетчер транзакций;
- нужен приоритет и защита от starvation;
- нужно защититься от ситуации "оба IRQ низкие одновременно".

### 7. Shared RST на два PN532

Сейчас `RST` общий.

Следствие:

- восстановление зависшего одного ридера через hard reset уронит оба;
- переход на сложную async-модель без soft-recovery стратегии может ухудшить надежность.

### 8. Отладка станет заметно сложнее

Синхронный polling сейчас прост в reasoning.

После almost interrupt-style появятся:

- гонки состояний;
- зависание флага события;
- mismatch между "UID был" и "вес уже изменился";
- редкие баги re-arm после нескольких циклов подряд.

Это нормальная цена, но ее надо учитывать заранее.

## Рекомендуемая стратегия внедрения

### Этап 1. Smart polling без IRQ

Сначала сделать то, что уже даст большой эффект без риска:

- уменьшить timeout inventory до `20..30 мс`;
- ввести round-robin опрос ридеров;
- ввести `WeightTrendState`;
- ввести `FastScan/SlowScan/ConfirmScan`;
- отделить `UID detect` от `full tag read`;
- собрать логи по весовым трендам и реальным заменам катушек.

Это должно дать заметное снижение лагов без форка PN532.

### Этап 2. Протокол записи и верификации

- реализовать `WriteRfid` на MCU;
- добавить readback verify;
- добавить статусы результата записи;
- ввести защиту от записи на "не тот UID";
- добавить кэш последней подтвержденной записи.

До этого этапа портал не должен делать auto-write.

### Этап 3. Политика автозаписи на портале

- хранить `desired_payload_hash`;
- хранить `last_written_payload_hash`;
- хранить `last_written_weight_g`;
- писать только при значимом изменении и в безопасном окне;
- ограничить частоту записи.

### Этап 4. Техническое исследование IRQ

Отдельный spike, без немедленной интеграции:

- проверить разводку IRQ на плате;
- проверить поведение линии на одном ридере;
- проверить поведение на двух ридерах;
- оценить, можно ли обойтись без форка библиотеки;
- если нельзя, оценить минимальный объем форка.

### Этап 5. Только затем prototype almost interrupt-style

Если spike успешен:

- сделать отдельный экспериментальный драйвер/state machine;
- не трогать сразу production `Pn532Driver`;
- включать через compile flag;
- сравнить latency, CPU impact и частоту ложных событий.

## Тесты и проверки

### Функциональные

- boot с уже установленной катушкой;
- boot без катушки;
- установка катушки в `Idle`;
- снятие катушки в `Idle`;
- активный режим, вес стабилен;
- активный режим, вес плавно убывает;
- активный режим, катушку реально снимают;
- краткий отрыв катушки от площадки;
- потеря метки без снятия веса;
- запись на метку с verify;
- смена UID в момент записи.

### Нагрузочные

- два ридера без меток;
- два ридера с метками;
- одновременный RFID + UART bursts;
- длинный runtime без TagDetected/TagRemoved;
- повторяющиеся write/read команды от портала.

### Для almost interrupt-style

- ложный IRQ после reset;
- обе IRQ активны одновременно;
- линия IRQ зависла в активном уровне;
- re-arm после нескольких циклов detect/remove;
- soft recovery без общего RST;
- hard recovery с общим RST.

## Решение по состоянию на сейчас

Для production-ветки рекомендован следующий порядок:

1. Оставить `SPI`.
2. Реализовать smart polling по весу и режиму.
3. Реализовать безопасный write pipeline с verify.
4. Включить автообновление веса на метке только после накопления логов и подбора порогов.
5. Almost interrupt-style считать отдельным R&D-треком, а не немедленной заменой текущего драйвера.

Это даст реальный выигрыш по отзывчивости и надежности без преждевременного усложнения PN532-части.
